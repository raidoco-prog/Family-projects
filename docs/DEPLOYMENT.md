# דיפלוימנט

## ההמלצה בקצרה

**Vercel (אפליקציה) + Supabase (בסיס נתונים, אימות, פוש) — בעלות 0 ₪ לחודש.**

בקנה מידה משפחתי שתי התוכניות החינמיות מספיקות בנוחות, אין שרת לתחזק, ה-HTTPS
מסודר מעצמו, וכל דחיפה ל-GitHub מעלה גרסה חדשה. הדבר היחיד ששווה כסף הוא דומיין
משלכם, בערך 40–60 ₪ לשנה, וגם הוא לא חובה.

**למה לא נייטיב.** אפליקציה נייטיבית קונה שני דברים אמיתיים — ווידג׳טים במסך

ושני קוד-בייסים. עבור משפחה, PWA מותקנת נותנת חוויה כמעט זהה. אם בעוד חצי שנה
יתברר שהפוש ב-iOS לא מספיק אמין — אפשר לעטוף את אותה אפליקציה ב-Expo בלי לכתוב
אותה מחדש.

## העלאה לאוויר, צעד אחר צעד

### 1. Supabase

1. פתח פרויקט חדש ב-[supabase.com](https://supabase.com), אזור `eu-central-1`
   (פרנקפורט — הכי קרוב לישראל, בערך 60ms).
2. הדבק את [`schema.sql`](./schema.sql) ב-SQL Editor והרץ.
   **על פרויקט שכבר יש בו סכימה** הרץ קודם [`reset.sql`](./reset.sql):
   הסכימה משתמשת ב-`create table`, ולכן הרצה חוזרת על טבלאות קיימות נכשלת.
3. Authentication → Providers → הפעל **Email** ו-**Google**.
   ל-Google נדרשת הכנה נפרדת ב-Google Cloud — ראה [הפעלת Google](#הפעלת-google)
   מיד למטה. בלעדיה כפתור «המשך עם גוגל» מוביל לדף JSON לבן עם
   `Unsupported provider: provider is not enabled`.
4. Authentication → URL Configuration → הוסף את כתובת ה-Production ואת
   `http://localhost:3000` לרשימת ה-Redirect URLs.
5. העתק מ-Settings → API את `Project URL`, את `anon key` ואת
   `service_role key`.

#### הפעלת Google

ספק ה-OAuth של גוגל לא נדלק בלחיצה אחת: צריך לייצר אצל גוגל זוג מפתחות
ולהדביק אותו ב-Supabase.

1. [console.cloud.google.com](https://console.cloud.google.com) → פרויקט חדש.
2. **APIs & Services → OAuth consent screen** → סוג **External** → מלא שם
   אפליקציה ואימייל תמיכה → שמור. כל עוד המסך במצב *Testing*, רק כתובות
   שהוספת תחת **Test users** יוכלו להתחבר — הוסף שם את כל בני המשפחה, או
   לחץ **Publish app**.
3. **Credentials → Create credentials → OAuth client ID** → סוג
   **Web application**.
4. תחת **Authorized redirect URIs** הדבק בדיוק את הכתובת הזאת, עם מזהה
   הפרויקט שלך:
   `https://<project-ref>.supabase.co/auth/v1/callback`
   זו כתובת של Supabase, **לא** של Vercel. גוגל חוזרת אל Supabase, ורק
   אחר כך Supabase מחזירה אל האפליקציה.
5. העתק את **Client ID** ואת **Client secret** אל Supabase →
   Authentication → Providers → Google → הדלק את המתג, הדבק, **Save**.

השינוי נכנס לתוקף מיד; אין צורך לפרוס מחדש ב-Vercel, כי שום דבר מזה לא
נכנס לקוד.

לזיהוי בלבד — כלומר להתחברות — **אין צורך להפעיל אף API**. זה משתנה ברגע
שרוצים לקרוא את היומן; ראה למטה.

#### סנכרון יומן גוגל

נדרש רק אם רוצים שהיומן האישי יזרום לאפליקציה. ראה `calendar-sync.sql`
ושלב 7 ב-[`PLAN.md`](./PLAN.md).

1. **הפעל את Google Calendar API** —
   [console.cloud.google.com/apis/library/calendar-json.googleapis.com](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com)
   → **Enable**.
   **זה חייב לקרות ראשון.** מסך ההרשאות מציג רק scopes של APIs מופעלים,
   ולכן בלי זה `calendar.readonly` פשוט לא קיים ברשימה — אין הודעת שגיאה,
   הוא רק חסר. הוספה ידנית של ה-scope בלי הפעלת ה-API נותנת הרשאה שגוגל
   מסרבת לכבד בפועל: `Google Calendar API has not been used in project…`.
2. **Data Access → Add or remove scopes** → סמן
   `https://www.googleapis.com/auth/calendar.readonly` → **Update** →
   **Save**.
3. הוסף ב-Vercel את `GOOGLE_CLIENT_ID` ואת `GOOGLE_CLIENT_SECRET` — אותו
   זוג שכבר הודבק ב-Supabase — ו**פרוס מחדש**.
4. באפליקציה: **הגדרות → «חיבור יומן גוגל»**, ואז **«סנכרון עכשיו»**.

ההרשאה מבוקשת ממסך ההגדרות ולא מההתחברות, בכוונה: אחרת כל ילד היה נדרש
לתת גישה ליומן שלו רק כדי להיכנס.

### 2. Vercel

1. חבר את ריפוזיטורי ה-GitHub ב-[vercel.com](https://vercel.com). Next.js מזוהה
   אוטומטית; **Root Directory** צריך להיות `web`.
2. הגדר משתני סביבה. הרשימה המלאה נמצאת ב-
   [`../web/.env.example`](../web/.env.example) — כולם נדרשים חוץ מהאחרון:

   | משתנה | היכן משיגים | חשוף לדפדפן | מה קורה בלעדיו |
   |---|---|---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API | כן | כל ניווט מוביל למסך `/setup` |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | אותו מקום | כן | כנ״ל |
   | `NEXT_PUBLIC_SITE_URL` | כתובת הפרודקשן שלך | כן | **אי אפשר להתחבר בכלל** — ראה למטה |
   | `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API | **לא — שרת בלבד** | הקרון נופל ב-500, שום התראה לא נשלחת |
   | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | `npx web-push generate-vapid-keys` | כן | אי אפשר להירשם להתראות |
   | `VAPID_PRIVATE_KEY` | מאותה פקודה | **לא — שרת בלבד** | הקרון מחזיר 500, שום התראה לא נשלחת |
   | `CRON_SECRET` | `openssl rand -hex 32` | **לא — שרת בלבד** | הקרון מחזיר 500, שום התראה לא נשלחת |
   | `VAPID_SUBJECT` | `mailto:you@example.com` | לא | אופציונלי; יש ברירת מחדל |
   | `GOOGLE_CLIENT_ID` | אותו זוג שהדבקת ב-Supabase | **לא — שרת בלבד** | סנכרון היומן נכשל ב-`invalid_client` |
   | `GOOGLE_CLIENT_SECRET` | מאותו מקום | **לא — שרת בלבד** | כנ״ל |

3. Deploy. כל דחיפה ל-`main` מעלה לפרודקשן, וכל Pull Request מקבל כתובת תצוגה
   מקדימה משלו.

> **`NEXT_PUBLIC_SITE_URL` הוא המלכודת המסוכנת ביותר כאן.** ממנו נבנית כתובת
> החזרה של Google ושל קישור הכניסה במייל, וברירת המחדל בקוד היא
> `http://localhost:3000`. אם שוכחים אותו הבנייה מצליחה, האתר עולה ונראה
> תקין — וכל ניסיון התחברות מנתב את בני המשפחה למחשב של עצמם. שום דבר לא
> מתריע על כך.

> `SUPABASE_SERVICE_ROLE_KEY` עוקף את כל מדיניות ה-RLS. הוא נחוץ רק לפעולות
> צד-שרת, ואסור שיופיע במשתנה עם קידומת `NEXT_PUBLIC_`. שים לב שייצוא הגיבוי
> דווקא **אינו** משתמש בו: הוא קורא דרך ה-session של המשתמש, כדי ש-RLS עצמו
> יבטיח שהקובץ מכיל משק בית אחד בלבד.

### 3. דומיין (אופציונלי)

דומיין ב-Cloudflare או Namecheap, הפניית DNS ל-Vercel, תעודת SSL אוטומטית.
כתובת כמו `mishpacha.app` נזכרת הרבה יותר טוב מכתובת `vercel.app` אקראית —
וזה משפיע על השימוש בפועל.

אם שינית דומיין, עדכן גם את `NEXT_PUBLIC_SITE_URL` ואת רשימת ה-Redirect URLs
ב-Supabase — אחרת ההתחברות נשברת בדיוק כמתואר למעלה.

### 4. תזכורות בקרון

**אחרי** שהאתר באוויר, הרץ את [`cron.sql`](./cron.sql) ב-SQL Editor. יש בו
שתי שורות להחליף: כתובת הפרודקשן והערך של `CRON_SECRET`. הוא מתקין
`pg_cron` ו-`pg_net`, ומתזמן קריאת POST ל-`/api/cron/notify` כל רבע שעה.

**למה pg_cron ולא Vercel Cron:** התוכנית החינמית של Vercel מגבילה קרון
להרצה אחת ביום — חסר תועלת לתזכורת «שעה לפני». pg_cron רץ כל רבע שעה בחינם.

הקרון עושה חמישה דברים בכל הרצה, ולא רק שולח:

1. פורס אירועים חוזרים על חלון של 60 יום ויוצר שורת תזכורת לכל מופע;
2. מעביר תזכורות שהגיע זמנן לתור היציאה;
3. מוסיף תזכורות משימות וסיכום בוקר;
4. מסנן לפי העדפות ושעות שקט;
5. שולח, ומנקה מנויי מכשיר שהדפדפן זרק.

התשובה היא JSON עם ספירה לכל שלב — `sent`, `skippedQuiet`, `noSubscription`,
`failed`, `expired`. זו הדרך המהירה ביותר לדעת למה משהו לא הגיע. במיוחד:
`noSubscription` גדול מאפס פירושו שיש בן משפחה שלא ביצע «הוסף למסך הבית».

לצפייה בהרצות: הקטע האחרון ב-`cron.sql` מכיל את השאילתה על
`cron.job_run_details`.

### 5. התקנה בטלפונים — אל תדלג

זו נקודת הכישלון היחידה של כל מודול ההתראות. באייפון Web Push עובד **רק**
אחרי «הוסף למסך הבית»; בספארי רגיל אין API בכלל, ואין מסלול גיבוי במייל —
כך הוחלט במפורש.

לכן העלייה לאוויר אינה נגמרת ב-Deploy אלא בכך שכל בן משפחה פתח את הכתובת,
לחץ «שתף → הוסף למסך הבית», ואז נכנס ל**הגדרות** ולחץ «הפעלת התראות».
מסך ההגדרות מזהה מכשיר שלא הותקן ומסביר מה לעשות, אבל הוא לא יכול לעשות
זאת במקומם.

הבדיקה הישירה היא בבסיס הנתונים: `select count(*) from push_subscriptions`
צריך להחזיר לפחות אחד לכל בן משפחה. `noSubscription` בתשובת הקרון מראה את
אותו דבר, אבל רק כשיש התראות ממתינות — אפס שם אינו הוכחה שכולם התקינו.

## בדיקה שהעלייה הצליחה

שבע בדיקות שמכסות את קריטריוני הקבלה שניתן לבדוק בקוד
([`REQUIREMENTS.md`](./REQUIREMENTS.md) §6). כדאי לעבור עליהן פעם אחת מיד
אחרי ה-Deploy, כי כמה מהתקלות כאן נראות כמו הצלחה.

1. **התחברות** — היכנס מטלפון, לא מהמחשב שממנו העלית. אם הדפדפן קפץ
   ל-`localhost`, `NEXT_PUBLIC_SITE_URL` שגוי.
2. **משק בית ובני משפחה** — צור משק בית והוסף את השאר. לכל אחד נוצר יום
   הולדת ביומן אוטומטית.
3. **הזמנות** — שלח קישור לבן משפחה אחד וודא שהוא נכנס ורואה את אותם נתונים.
4. **הלולאה** — הורד פריט מלאי מתחת לסף וודא שנפתח פריט קניות מעצמו; סמן
   «נקנה» וודא שהמלאי חזר ליעד.
5. **סנכרון חי** — פתח את רשימת הקניות בשני מכשירים; הוספה באחד צריכה
   להופיע בשני בלי רענון.
6. **התראות** — קבע אירוע לעוד שעה וחצי, המתן להרצת הקרון הבאה, וודא
   ש-`sent` בתשובה גדול מאפס ושההתראה הגיעה לשני ההורים.
7. **גיבוי** — הגדרות → «הורדת גיבוי». הקובץ צריך להכיל את בני המשפחה
   והאירועים שהזנת.

קריטריון הקבלה השמיני — שהמשפחה השתמשה שבועיים ברצף בלי לחזור לפתק על
המקרר — הוא היחיד שאי אפשר לבדוק כאן, והיחיד שקובע אם הפרויקט הצליח.

## שני דברים שאסור לדלג עליהם

**גיבויים.** בתוכנית החינמית של Supabase שמירת הגיבויים מוגבלת בזמן.
באפליקציה יש **הגדרות → הורדת גיבוי**, שמוריד קובץ JSON אחד עם כל נתוני
הבית (`/api/backup`). זה הפתרון הידני, והוא מספיק אם באמת לוחצים עליו.
מי שרוצה אוטומציה: `pg_dump` שבועי ב-GitHub Actions שמעלה לדרייב או ל-S3.

שים לב שהגיבוי אינו כולל מנויי פוש — אלה סודות של מכשיר ואין מה לשחזר מהם.
אחרי שחזור, כל אחד יצטרך להפעיל התראות מחדש בטלפון שלו.

**השבתה בגלל חוסר פעילות.** פרויקט Supabase חינמי מושהה אחרי כשבוע ללא פעילות
ודורש הפעלה ידנית. סביר שהקרון לבדו מספיק: כל רבע שעה הוא מפעיל את
`/api/cron/notify`, שקורא ל-Supabase דרך ה-API — כלומר תעבורה אמיתית ולא רק
פעילות פנימית בבסיס הנתונים. הקריטריון המדויק שלפיו Supabase מודדים פעילות
אינו מתועד באופן שאפשר להסתמך עליו, ולכן אם ההשהיה בכל זאת קורית, בדיקת
בריאות יומית מ-GitHub Actions פותרת את זה.

## אם בכל זאת אחסון עצמי

רלוונטי כשחשוב שהמידע — במיוחד התורים הרפואיים — לא ישב אצל ספק חיצוני.

- **חומרה:** Hetzner CX22 בכ-€4 לחודש, או Raspberry Pi 5 בבית עם
  Cloudflare Tunnel (חושף את השירות בלי לפתוח פורטים בראוטר).
- **הרצה:** Docker Compose עם שלושה שירותים — אפליקציית Next.js, Postgres,
  ו-Caddy כ-reverse proxy עם HTTPS אוטומטי. [Coolify](https://coolify.io)
  נותן חוויית PaaS דמוית-Vercel מעל השרת שלכם, כולל דיפלוי מ-Git.
- **המחיר האמיתי אינו כספי:** עדכוני אבטחה, גיבויים, וניטור הופכים לאחריותכם.
  בפרויקט של סופי שבוע זו הסיבה השכיחה ביותר לנטישה.
